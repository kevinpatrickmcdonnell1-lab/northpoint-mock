# Requirements traceability: interview brief R1–R10

Each row maps one requirement from the brief to where it is implemented, the tests that prove it, and how to show it live in the mock (real set, R01–R10, after **Reset demo**). `tests/test_requirements_trace.py` parses this file and fails if any test cited here is not collected by pytest, so the table can't silently go stale. Every cited test passes in `make test`.

Condensed requirements:
- **R1** Per patient, separate fields: clinical priority (routine / expedited / urgent review / unable to determine); identity and coverage (verified / pending / conflicting / inactive as applicable); PA requirement (required / not required / unknown); clinical criteria evidence (supported / not met / insufficient or conflicting) with rule IDs and file/page references; next action with a human owner.
- **R2** "Supported" means the packet supports the sample rule, never a payer approval; "not met" is not a payer denial.
- **R3** All simultaneous holds shown; clinical escalation proceeds while intake verifies identity or coverage and while reports are requested.
- **R4** PA submission only when PA is required, identity and coverage are verified, and required evidence is supported.
- **R5** A no-PA plan skips only the PA step; scheduling still needs identity, coverage, the signed order, adequate clinical evidence and any clinical review cleared.
- **R6** A failed or uncertain gate is visibly blocked; the audit trail keeps source references and the next owner.
- **R7** Source evidence, payer decisions and clinician clearance kept separate; simulated events record role, timestamp, decision and an audit entry, are shown as simulated, and never relabel PDF evidence.
- **R8** PA-required scheduling waits for the simulated approval and every other gate.
- **R9** Every handoff names the work item, the receiving system, its recorded output and the gates checked.
- **R10** No new clinical treatment decisions.
