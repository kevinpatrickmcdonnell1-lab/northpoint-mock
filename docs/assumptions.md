# Assumptions and interpretation calls

Every judgment call on rule wording, with its rule ID. Flags A1–A2 live in `config/workflow.yaml`. They are config switches to confirm in discovery; a change takes a restart plus Reset, so don't flip them mid-demo.

## From PLAN §7.4
| ID | Rule | Call |
|---|---|---|
| A1 | G-CLIN | `routine_requires_clinical_clearance: false`. PRI-3 orders need no nursing sign-off before scheduling. *Ask Intake/Clinical.* When flipped on, routine cases get `CLIN_ROUTINE_REVIEW` → Clinical Review RN. |
| A2 | G-EVID | **Changed 2026-11-27 to follow the brief (R5):** `no_pa_evidence_gate: [DOC-1, QUAL-1, QUAL-2, REPEAT-1]`. A no-PA plan (PPO) skips only the PA step; identity, coverage, the signed order and the clinical evidence still gate scheduling, and a not-met or insufficient rule generates its usual action. HMO-1 stays plan-specific. *Was:* `[DOC-1]`, with QUAL/REPEAT advisory for PPO. The flag stays a config switch to confirm in discovery. |
| A3 | PRI-4 | A newer note that contradicts older timing without documenting a change → PRI-4, not an override. |
| A4 | HMO-1 | Only an out-of-window resting ECG → *insufficient* (same action: request a current report). |
| A5 | ID-1 | Name differences other than case/punctuation/whitespace/missing middle initial (nicknames and token order included) → conflict for human review. |
| A6 | COV-1 | A benefits response with an unspecified product → coverage *pending*, not conflicting. |
| A7 | Metrics | Business days = Mon–Fri, no holiday calendar. |
| A8 | COV-1 | A benefits response dated after the evaluation date is ignored. |

## Build-time calls (2026-11-24)
| ID | Where | Call | Why |
|---|---|---|---|
| B1 | `app/models.py` | Extraction `fields` not listed in a packet default to `false` / `not_stated` / `null`. | PLAN §6.2: "set fields that aren't listed to `not_stated` or `false`." The defaults mean "absent", never an outcome. |
| B2 | `app/models.py` | `fields` are validated against the model for their `doc_type`, with `extra="forbid"` at every level. A quote must cite a page in its document's `pages`. | Catches facts filed under the wrong type, and broken page references, before any rule runs. |
| B3 | `app/models.py` | Besides `extra="forbid"`, raw JSON is scanned for an explicit `DERIVED_KEYS` list. | Invariant 2: belt and braces, with a readable error path. |
| B4 | `app/models.py` | `IDENTITY_RESOLUTION` requires confirmed values, an Epic reference **and** a note. `BENEFITS_RESPONSE` requires a payload. `simulated` is `Literal[True]` and a DB CHECK constraint. | Invariant 3 and §6.3 ("note required"). |
| B5 | `app/policy.py` | Product normalization lowercases and strips punctuation and extra whitespace, but never drops words. | "Harborstone Health Commercial" must stay unresolved (P09). No prefix or fuzzy matching. |
| B6 | config path | PLAN §3 mentions `policy/sc-card-1.1.yaml`; §4 and CLAUDE.md say `config/policy_sc_card_1_1.yaml`. The latter is used. | CLAUDE.md wins. |
| B7 | `rules/common.py` (§7.2 "only signed documents") | The signature requirement applies to clinical documents (referral, order, clinician note, ECG reports). Registration, card and benefits responses are administrative records with no clinician signature. They are used by ID-1/COV-1/plan resolution and labelled "n/a (admin)" in the UI. | Otherwise no coverage or identity rule could ever pass. |
| B8 | PRI (§7.2) | A candidate "addresses timing/severity" if it states any of: urgent or expedited request, material increase date, a trajectory other than `not_stated`, or timing text. "Contradicts" means both trajectories are stated and differ. A **documented material change** means the newer note states a `material_increase_date`. An explicit expedited/urgent request in a newer note is not a contradiction. | P06: a clinician asking for expedited review over a plain referral is an escalation, not a conflict. P05: the documented change overrides. P08: same-day disagreement → PRI-4. |
| B9 | QUAL-1 | "Order indication matches the complaint" is a text match on the order's indication: `exertional` + chest discomfort/pain/pressure/tightness, or `exertional` + dyspnea/shortness of breath. | P10's indication "chest pain" (no exertional term) does not match. That doesn't matter here, because the complete nonexertional assessment makes QUAL-1 NM. |
| B10 | COV-1 "two in-window responses disagree" | Read as two responses with the **same newest** response date that disagree. A newer response supersedes an older one. | Otherwise the scripted P04 transition (a simulated E&B on 10-01 replacing the 09-23 mismatched response) could never verify coverage, which contradicts §6.3. |
| B11 | COV-1 member match | Expected member ID = the human-confirmed `member_id` from an `IDENTITY_RESOLUTION` event if present, else every registration/card member ID. The newest response must equal it exactly. Coverage verification also requires plan resolution to be `resolved`. | P04 stays conflicting after the identity resolution until a matching E&B arrives (§6.3). "Exact product" requires the product to be resolved. |
| B12 | Actions (P04) | §6.3's next-action column for P04 lists only "Verify identity". The coverage column says Conflicting, so the engine also emits `COV_CONFLICT` (Reconcile member mismatch → Intake). The golden test expects both. | Each hold gets an owner, and coverage is genuinely conflicting. This reads the table's terse action column; it doesn't change the table. |
| B13 | Actions | When any gating criterion is NM, only `EVID_NOT_MET` is emitted. Missing-report requests are suppressed, because chasing documents for a case that does not meet criteria wastes outreach. DOC-1 and QUAL-1 both missing because there's no order → one order request. | P07, P10 and P09 as in §6.3. |
| B14 | Actions after clinical events | `reviewed_hold` → `CLIN_REVIEWED_HOLD` (Triage RN; scheduling still held). `not_cleared` → `CLIN_NOT_CLEARED`. `cleared_for_scheduling` → no clinical action. Priority itself never changes because of an event. | §6.3 P03/P08. Triage acts without rewriting the source evidence. |
| B15 | PA lifecycle | PA prep ready + no payer decision → `PA_READY`. `pended` → `PA_AWAITING`. `denied` → `PA_DENIED` (SIMULATED). The engine does not read the outbox, so a sent PA packet does not change the action. The outbox shows the submission. | Keeps the engine pure (facts + events + policy only). |
| B16 | Metrics | Admin-readiness date = the latest simulated event date on the case, or the evaluation date if ready at baseline. P08 counts as admin-ready, because G-CLIN is excluded (§7.3). | §8.5. |
| B17 | Handoffs | Gated: scheduling (all six gates) and PA packet (PA-prep gates). Ungated (always allowed when applicable): triage notification, identity task, missing-info request. Idempotency key = packet + kind + gate/event snapshot hash, or a payload hash for ungated items. | §8.4. A new simulated event changes the snapshot, so a re-send after a real change is a new handoff. |
| B18 | Data layout (§6.4) | Dataset auto-selects `real` once `data/extractions/*.json` exists; `NORTHPOINT_DATASET` overrides. Tests always use the mock set. | Keeps the mock set as a regression suite without a manual switch. |
| B19 | Combined PDFs | Extractions cite the ORIGINAL file and page. An optional `data/packets/manifest.yaml` gives each packet's page range, and `check` rejects cited pages outside it. | §6.4.1. Tested by merging P01 and P02 into one PDF: same outcomes, refs point at the combined file. |
| B20 | Stretch: delivery | A handoff is recorded once (gated, idempotent). Delivery attempts are separate append-only rows. A SIMULATED receiver outage fails attempts; after `delivery_max_attempts` (3) the handoff is dead-lettered for the integration owner, and only a human requeue replays it with the same payload and key. Retries never re-gate, re-record or duplicate. | §11 production note: "idempotent handoffs with retry and dead-letter queues". |
| B21 | Stretch: site | `ordering_site` is intake metadata on the extraction (printed in the page footer). Never used by any rule (mutation-tested). Used only for the queue filter and per-site metrics. | §1.6.4 / §10 Stretch: show which sites drive the holds without letting site change a decision. |

## Seam hardening (2026-11-27, branch `fix/seam-hardening`)
| ID | Where | Call | Why |
|---|---|---|---|
| A3a | PRI (PLAN A3) | If any older signed candidate has a higher tier (PRI-1 > PRI-2 > PRI-3) than the newest candidate, the result is PRI-4, and the reason names both documents and their tiers. A documented material change in the newer note does not excuse it. | No current field can document a deliberate downgrade ("urgent review no longer needed"), so a newer note that simply doesn't repeat an urgent/expedited request is unresolved, not an override. Under-triage is the costly error. |
| B25 | Handoffs (Fix 3) | A repeat "Send to scheduling" while a handoff is active returns `already_sent` and records no handoff. The `handoff_attempt` audit row is still written, as for every attempt (the audit is not a handoff). An identical idempotency key still reports `already_recorded`. | "Records nothing" is read as no outbox row, no JSON file and no `handoff_sent` audit. Keeping the attempt row preserves "every attempt is audited". |
| B26 | Handoffs (Fix 4) | A recall is checked only after a simulated event, because only events change a case's state at runtime. Re-running the engine after a YAML edit plus restart does not trigger recalls; the demo note says not to flip flags live (and Reset clears handoffs anyway). The recall goes to the same receiving system as the handoff it recalls, and is itself ungated. | Readiness can change only through facts (immutable), events or policy. Policy changes need a restart, and the demo resets. |
| B27 | Config (Fix 5) | "Known rule ID" is read narrowly per slot. `plans.*.extra` accepts only plan-extra rules (today `HMO-1`), and `no_pa_evidence_gate` accepts only evidence rules (`DOC-1`, `QUAL-1`, `QUAL-2`, `REPEAT-1`, `HMO-1`). | A known but wrong-kind ID (e.g. `ID-1` in the evidence gate) would still crash or silently do nothing; the slot decides what is meaningful. |
| B28 | Config (Fix 5) | The config hash covers the exact bytes of both YAML files, so a comment-only edit changes it. | The audit should prove which file content was in force, not just which parsed values. |
| B29 | ID-1 (Fix 6) | A confirmed value that appears on no page is still accepted and flagged ("not found in packet"); identity status is unchanged. The check covers every confirmed field, not just conflicting ones, and matching uses the same normalization as conflict detection (names per A5, DOB as ISO date, others case-insensitive). | Epic is the authority (PLAN §1.6.5), so the mock can't overrule it, but a keying error must be visible. |
| B30 | COV-1 / UI (Fix 7) | A8 is unchanged: late responses are still ignored. The UI form refuses to create one, but `Service.simulate` does not, so the engine's handling (named in the reason text) remains the single rule. An in-packet response counts as late if either its `response_date` or its document date is after the evaluation date. | Matches `usable_docs` (document date) and `_responses` (response date), so nothing either filter drops goes unnamed. |
| B31 | Evidence refs (Fix 8) | A judgment field counts as "set" when its value is not `None`, `False` or `not_stated` (the B1 "absent" defaults), so `complete=True` (the resting-ECG default) is reported if unquoted. A `False` judgment is not reported. | B1 defaults mean "absent"; reporting them would bury the real gaps. |
| B32 | Actions (brief fix 1) | On a no-PA plan, a not-met gating rule emits the usual `EVID_NOT_MET` action (owner: Auth Specialist, "Do not prepare PA. Review with ordering clinician"). The code and owner are kept so not-met is handled the same way on every plan; "do not prepare PA" is trivially true for a plan with no PA step. | One review path for not-met. Who reviews not-met PPO orders (Auth or Intake) is worth asking in discovery. |
| B33 | Labels (brief fix 3) | Display words follow the brief (R1): PRI-1 "Urgent review" (was "Urgent"); criteria status `I` displays as "Insufficient or conflicting" (was "Insufficient"). The internal code stays `I`, because the engine has one status for both cases. Reason texts say which applies (e.g. "Insufficient on HMO-1", or "Benefits responses dated … disagree"). The scheduling payload's `clinical_priority` is the lowercased label ("urgent review"). Identity uses only verified / pending / conflicting; "inactive" applies to coverage alone. | The brief's vocabulary is what the panel will listen for. Splitting `I` into two codes would change the golden tables and is not needed to show the distinction. |

## Human review of extracted facts (2026-11-27)
| ID | Where | Call | Why |
|---|---|---|---|
| B34 | Fact checks | Four checks: quote not found on its page; signer's surname missing from the `signer` quote; a date fact whose quote states a different date (ISO, US and "September 30" forms, with year optional); a copied text field (`procedure`, `timing_text`, `plan_product_raw`, `member_id`) whose value isn't in its own quote. A "signed but no signature quote" check was left out: it fires on almost every mock document (signatures were authored without quotes), so it would bury the real flags. | Each check targets a quote that exists but doesn't back its value, the class of the R01 signer bug. Classified fields (enums, booleans) are paraphrases by design and are not checked. |
| B35 | Flags | A flag never changes a fact or a result, and the engine never sees flags. It stays open until a person confirms or corrects that fact. Confirming a flagged fact needs a note saying why it is right. Flags don't block handoffs (making the facts behind a gate need review first is a later, opt-in step). | Flags route work to people; making them gates would change both golden tables. |
| B36 | Corrections | A correction must quote page text from one of that document's own pages (found by the same normalized match as `check_extractions`), give a reason, and name a role and a person. It replaces that field's value *and* its quotes in the reviewed view. The source row in `cases` is never changed, and corrections are stored in the append-only `fact_reviews` table. | Keeps invariant 4 and keeps every fact traceable to a page, even after a human edit. |
| B37 | Who may review | Reviewer roles: Intake Coordinator, Auth Specialist, Clinical Review RN, Clinical Triage RN, Cardiologist. Clinical facts (priority fields except `timing_text`, clinician-note findings, ECG interpretation fields, order indication) need a clinical role to confirm or correct. Dates, signer, coverage and procedure name can be reviewed by any role. | Mirrors `ALLOWED_ROLES` for clinical review decisions. Worth asking in discovery: who at Northpoint owns fact QA? |
| B38 | Identifiers | Identifier fields (`name`, `dob`, `mrn`, `packet_id`) can be confirmed but not corrected here; the UI points to Identity resolution. | Invariant 7: correcting a DOB on a page would be a back door around never auto-selecting between conflicting identifiers. |
| B39 | Audit | Reviews are audited under the existing `correction` audit kind, with `action` confirm/correct and before/after values. A correction re-evaluates the case (a `state_change` diff) and runs the same recall check as a simulated event. | Reusing the kind avoids altering the audit table's CHECK constraint, which SQLite can't change on an existing database. |
